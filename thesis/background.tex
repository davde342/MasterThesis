\chapter{Background}
\label{ch:background}

This chapter begins by introducing the foundational concepts of \ac{DBI} within a Windows environment necessary to understand the proposed work.
Subsequently, it analyzes state-of-the-art frameworks utilized for \ac{DBI}. This overview is essential for contextualizing the compilation targets selected for our Domain-Specific Language (DSL), which are discussed in detail in \fullref{ch:method}.

As discussed in \fullref{ch:introduction}, \ac{DBI} allows us to change the runtime behavior of a binary, injecting a compiled payload into an existing executable.

\section{The Application Binary Interface (ABI)}
\label{sec:abi}

Ensuring interoperability between distinct compiled modules—regardless of the specific compilers or programming languages used—requires a \emph{standardized low-level interface}.
To allow instrumentation payloads to safely interact with a target process without causing unexpected runtime crashes, it must strictly adhere to the Application Binary Interface (ABI).
The ABI defines the low-level rules for how functions interact at the assembly level, including how parameters are passed to a function, how return values are retrieved, which entity is responsible for cleaning up the stack (the caller or the callee), and the \emph{register preservation contract} that dictates which registers must remain preserved across function boundaries.
These rules are formalized as \emph{Calling Conventions}.
The complexity of ABI compliance and the risk of runtime crashes depend heavily on the target architecture.

\subsection{Windows x86 (32-bit) Architecture}
In 32-bit environments, multiple calling conventions coexist~\cite{doc:msvc_x86_calling_conventions}, requiring developer-level alignment between the instrumentation target function and the injected payload implementation.
The most common conventions include:
\begin{itemize}
	\item \texttt{\_\_cdecl}: Arguments are pushed onto the stack from right to left, and the \emph{caller} cleans the stack.
	This is the default convention for C/C++ binaries.
	\item \texttt{\_\_stdcall}: The standard convention for the Windows \ac{API}.
	Arguments are pushed right to left, but the \emph{callee} cleans the stack.
	\item \texttt{\_\_fastcall}: The first two arguments are passed in the \texttt{ECX} and \texttt{EDX}, while the rest are placed on the stack. The \emph{callee} must clean the stack
	\item \texttt{\_\_vectorcall}: An extended convention designed for pass several floating-point arguments, the first two integer type arguments found in the parameter list from left to right are placed in ECX and EDX, respectively and up to six vector arguments in \texttt{XMM0}--\texttt{XMM5}. The \emph{callee} must clean the stack
	
\end{itemize}
Across these 32-bit conventions, registers are typically divided into \emph{caller-saved registers} (\texttt{EAX}, \texttt{ECX}, and \texttt{EDX}), which the caller assumes can be freely overwritten by the called function, and \emph{callee-saved registers} (\texttt{EBX}, \texttt{ESI}, \texttt{EDI}, and \texttt{EBP}), which the called function is contractually required to preserve and restore before returning.

Understanding and matching these different conventions is critical for \ac{DBI} on Windows x86 processes.


\subsection{Windows x64 (64-bit) Architecture}
\label{subsec:abi_x64}
Windows x64 defines a single native calling convention~\cite{doc:msvc_x64_calling_conventions}.
The compiler accepts \texttt{\_\_cdecl}, \texttt{\_\_stdcall} and \texttt{\_\_fastcall} for compatibility but ignores them; \texttt{\_\_vectorcall} remains in effect on x64 and must be matched exactly when a target uses it.
The default convention works as follows:
\begin{itemize}
	\item Arguments are assigned to positions. Position $i\in\{1,\dots,4\}$ is passed in \texttt{RCX}, \texttt{RDX}, \texttt{R8}, \texttt{R9} if the argument is an integer or a pointer, and in \texttt{XMM0}--\texttt{XMM3} if it is floating point. In \texttt{f(int a, double b, int c, double d)}, \texttt{a} travels in \texttt{RCX}, \texttt{b} in \texttt{XMM1}, \texttt{c} in \texttt{R8} and \texttt{d} in \texttt{XMM3}.
	\item Further arguments are pushed on the stack. The caller removes them, reserves 32 bytes of \emph{shadow space} before every call, and keeps the stack 16-byte aligned.
	\item Integer and pointer results are returned in \texttt{RAX}, floating-point results in \texttt{XMM0}.
	\item \emph{Volatile (caller-saved)}: \texttt{RAX}, \texttt{RCX}, \texttt{RDX}, \texttt{R8}--\texttt{R11}, \texttt{XMM0}--\texttt{XMM5}. \emph{Non-volatile (callee-saved)}: \texttt{RBX}, \texttt{RBP}, \texttt{RDI}, \texttt{RSI}, \texttt{R12}--\texttt{R15}, \texttt{XMM6}--\texttt{XMM15}; a function that uses them must save them in its prologue and restore them before returning.
\end{itemize}

\texttt{\_\_vectorcall} keeps the positional scheme but extends it: vector-type arguments among the first six are passed by value in \texttt{XMM0}--\texttt{XMM5}, whereas the default convention passes an \texttt{\_\_m128} by reference and uses \texttt{XMM0}--\texttt{XMM3} only.

Having one convention removes the stack-cleanup mismatches typical of x86, but not every error: a detour must still declare the target's exact parameter list and return type.


\section{Dynamic-Link Libraries}
\label{sec:dll_foundations}

To perform \ac{DBI} in modern Windows environments, external instrumentation code must execute directly within the target application's execution context. In Windows, this is commonly achieved through Dynamic-Link Libraries (\acp{DLL}) and process injection.

\subsection{Static vs. Dynamic Linking}
Under the \emph{static linking model}, all external functions and dependencies required by an application are permanently integrated into the final executable (EXE) file at link time. While this ensures that the application is fully self-contained, it introduces severe inefficiencies: every program on disk contains redundant copies of library code, and multiple running programs allocate separate physical RAM pages for the same helper routines.

\emph{Dynamic linking} instead defers the binding of external library functions until runtime~\cite[Ch.10]{book:levine2000linkers}. A \ac{DLL} is an independent binary executable module that contains functions, resources, and data that can be called dynamically by other modules or applications. Rather than duplicating library code inside every host application on disk, the operating system maintains a single standalone \ac{DLL} file. When multiple processes load the library, the operating system loader maps the same physical code pages in RAM into each process's virtual address space, drastically reducing both disk footprint and physical memory consumption.


\subsection{Address Space Isolation and Virtual Memory Mapping}
\label{subsec:address_space_isolation}
In modern operating systems, every running application is allocated an isolated, private virtual address space. This architectural boundary prevents one application from directly reading, writing, or corrupting the code or memory space of another.

To enable shared libraries to execute without violating this isolation model, the operating system loader utilizes \emph{virtual memory mapping}. When a process loads a \ac{DLL}, the loader maps the linear address range of the compiled \ac{DLL} binary directly into the virtual address space of that process. Once mapped, functions within the \ac{DLL} execute natively within the host application's memory context, allowing them to directly read, write, and manipulate the target's memory and execution state.

\subsection{DLL Injection and Instrumentation Lifecycle}
\label{subsec:dll_injection}

Because virtual memory mapping allows a \ac{DLL} to execute inside a process's private address space, \acp{DLL} represent the primary vehicle for Windows \ac{DBI}. However, because target applications are unaware of our instrumentation, the framework must force the target to load the payload from the outside.
This is achieved through \emph{\ac{DLL} Injection}~\cite{mitre:t1055_001}. The standard injection technique leverages the Windows \ac{API} functions \texttt{VirtualAllocEx}, \texttt{WriteProcessMemory}, and \texttt{CreateRemoteThread} targeting \texttt{LoadLibrary}. The injector process allocates memory in the remote target, writes the absolute path of the instrumentation \ac{DLL}, and spawns a remote thread pointing to \texttt{LoadLibrary}, which executes within the target process and triggers the OS loader to map the \ac{DLL}.
Once mapped into the target process, \acp{DLL} provide an automatic lifecycle management mechanism via the entry point function, \texttt{DllMain} (\cref{lst:dllMain}):
\begin{enumerate}
	\item \emph{Automatic Initialization (\texttt{DLL\_PROCESS\_ATTACH}):} Invoked automatically by the Windows loader immediately after the \ac{DLL} is mapped into the process, allowing the framework to resolve target APIs and apply hooks.
	\item \emph{Automatic Cleanup (\texttt{DLL\_PROCESS\_DETACH}):} Invoked automatically when the \ac{DLL} is unmapped (e.g., during module ejection via \texttt{FreeLibrary}), allowing the framework to safely revert patches and deinitialize resources.
\end{enumerate}
	
	\begin{lstlisting}[language=C++, caption={DllMain code for attaching/detaching instrumentation}, label={lst:dllMain}, basicstyle=\ttfamily\footnotesize, breaklines=true]
		BOOL APIENTRY DllMain (HMODULE hModule,
		DWORD   ul_reason_for_call,
		LPVOID  lpReserved)
		{
			switch (ul_reason_for_call)
			{
				case DLL_PROCESS_ATTACH:
				// Instrumentation framework-specific logic for injecting instrumentation
				break;
				case DLL_PROCESS_DETACH:
				// Instrumentation framework-specific logic for disabling instrumentation
				break;
			}
			
			return TRUE;
		}
	\end{lstlisting}

\section{Paradigms of DBI}

Modern \ac{DBI} engines generally fall into two broad architectural paradigms:
\begin{itemize}
	\item \emph{Inline Hooking:} this paradigm involves modifying the original execution flow via localized jumps.
	It patches specific functions in memory, redirecting execution to a custom payload, the \emph{hook}, before returning to the original flow.
	\item \emph{Code-Cache Based \ac{DBI}:} rather than modifying the original binary in place, \ac{DBI} engines copy, recompile, and execute instructions inside a localized sandbox known as a Code Cache.
\end{itemize}

\subsection{CPU State Preservation}
\label{subsec:state_pres}
\ac{DBI} changes the execution flow of a thread at an arbitrary moment, so the execution of injected code must leave the thread's \emph{machine state} as it found it: the general-purpose registers, the flags register and the stack.
Engines differ in \emph{who} guarantees this, and the answer depends on whether engine-generated code runs between the target function and our instrumentation payload.
\begin{itemize}
	\item \emph{Direct-jump hooking}: The prologue of the target is overwritten with a direct jump to the instrumentation payload, and no engine code runs in between. The payload is ordinary compiled code state preservation is thus delegated to the developer that must respect the \ac{ABI} of the target.
	\item \emph{Dispatcher-mediated hooking}: Before reaching our code the execution jumps into an engine-generated thunk, which calls a generic C dispatcher. A thunk is not \ac{ABI}-conformant code, and the dispatcher may use every volatile register, so the instrumentation engine must automatically save the whole context and restore it before control reaches our code.
	\item \emph{Code-cache \ac{DBI}}: Every instruction of the program is rewritten: engine generated code always runs before reaching our instrumentation code, so similarly to Dispatcher-mediated hooking, the engine continuously must save/restore the state.
\end{itemize}

\section{Inline Hooking}
\label{sec:inline_hooking}

A standard inline hook consists of three primary logical components:
\begin{enumerate}
	\item \emph{The Target:} the original function whose execution we wish to intercept.
	The goal is to patch the first 5 to 7 bytes of the target function with an unconditional jump (\texttt{JMP}) to a user-defined payload.
	These initial bytes are restored to the target function once the instrumentation is complete and the framework detaches from the host process.
	\item \emph{The Detour (or Payload):} the custom function injected by the instrumentation framework.
	This function receives the execution flow, inspects the target function's arguments or return value, performs the desired analysis or policy enforcement, and then dictates whether the execution should continue or be blocked.
	\item \emph{The Trampoline:} in the paradigm of inline hooking, placing an interception branch (\texttt{JMP}) inherently corrupts the target function's prologue.
	To maintain execution continuity, all inline instrumentation frameworks must implement an Out-of-Line Execution Bridge, universally referred to as a \emph{``Trampoline''}.
	Conceptually, the trampoline is a dynamically allocated, executable memory buffer that must fulfills two architectural mandates: it securely relocates the displaced prologue instructions and unconditionally routes the instruction pointer back to the unpatched remainder of the target function.
\end{enumerate}

\subsection{Direct-Jump Hooking: Microsoft Detours and MinHook}
\label{subsec:bare_metal_hooking}
Frameworks like Microsoft Detours~\cite{DBLP:conf/usenix-nt/HuntB99} and MinHook~\cite{repo:minhook} are the well-known standard for Windows x86/x64.
As we have introduced in \cref{subsec:state_pres}, in Direct-Jump Hooking no engine-generated code is executed before reaching the Detour.
The detour is ordinary compiled code that follows the platform \ac{ABI}: its prologue and epilogue preserve the non-volatile registers. It holds only if the developer use for the detours exactly the convention, parameters and return type of the target as illustrated in \cref{lst:detours}; otherwise arguments are read from the wrong registers, the result is returned in the wrong one or, on x86, the stack is left unbalanced.

\begin{lstlisting}[language=C++, caption={Detours and MinHook target function pointer declarations.}, label={lst:detours}, basicstyle=\ttfamily\footnotesize, breaklines=true]
	// Strict function pointer definition required by Detours
	static int (WINAPI * TrueMessageBoxW)(HWND, LPCWSTR, LPCWSTR, UINT) = MessageBoxW;
	
	// Strict function pointer definition required by MinHook
	typedef int (WINAPI * MESSAGEBOXW)(HWND, LPCWSTR, LPCWSTR, UINT);
	MESSAGEBOXW fpMessageBoxW = NULL;
\end{lstlisting}

Furthermore, to correctly access arguments and clean up the stack according to the ABI, the detour function must strictly mirror the original signature, as shown in \cref{lst:detours2}.

\begin{lstlisting}[language=C++, caption={Strict ABI compliance in the hooked detour function.}, label={lst:detours2}, basicstyle=\ttfamily\footnotesize, breaklines=true]
	// Detours (same for MinHook)
	int WINAPI HookedMessageBoxW(HWND hWnd, LPCWSTR lpText, LPCWSTR lpCaption, UINT uType)
\end{lstlisting}

The code structure for the hooked function is identical in both frameworks.

In \cref{lst:detours3}, the goal is to intercept a target process's call to \texttt{MessageBoxW} and modify the displayed dialog with custom text (\texttt{customCaption}) and altered options (\texttt{modifiedType}) during the PRE-LOGIC phase.

After this, the trampoline is called, the original function is executed with the modified arguments, and control is returned to the hooked version (POST-LOGIC).

Here, we intercept the user's choice (\texttt{result}), forcing a ``yes'' outcome even if the user pressed ``no'', and return the final result to the target process:

\begin{lstlisting}[language=C++, caption={Detours/MinHook Hooked function structure}, label={lst:detours3}, basicstyle=\ttfamily\footnotesize, breaklines=true]
	// Detours (same for MinHook)
	int WINAPI HookedMessageBoxW(HWND hWnd, LPCWSTR lpText, LPCWSTR lpCaption, UINT uType)
	{
		// PRE-LOGIC
		UINT modifiedType = MB_YESNO;
		LPCWSTR customCaption = L"Hooked! Please choose:";
		
		// Call to the trampoline
		int result = TrueMessageBoxW(hWnd, lpText, customCaption, modifiedType);
		// POST-LOGIC
		if (result == IDNO) 
		{
			std::cout << "[HOOK POST-LOGIC] Intercepted IDNO (No). Changing result to IDYES (Yes)!"
			<< std::endl;
			result = IDYES; 
		}
		else if (result == IDYES)
		{
			std::cout << "[HOOK POST-LOGIC] Intercepted IDYES (Yes). Nothing to do."
			<< std::endl;
		}
		
		return result;
	}
\end{lstlisting}

\subsection{Dispatcher-Mediated Hooking: Frida-Gum}
\label{subsec:frida_arch}
Frida-Gum~\cite{repo:frida-gum} is the underlying low-level C library of the Frida instrumentation toolkit, representing a modern, multi-architecture approach to Inline Hooking.

At the core of Frida-Gum engine is a centralized execution dispatcher: when an intercepted target function is invoked, execution jumps not directly to the detour function, but into a dynamically generated entry thunk. The entry thunk saves the CPU state into an architecture-agnostic \texttt{GumCpuContext} structure and trigger a dispatcher, that automatically handle the entire hook execution flow.

Unlike traditional single-paradigm frameworks like Detours or MinHook, Frida-Gum provides a flexible, dual-paradigm Interceptor \ac{API} comprising \emph{Invocation Listener Mode} and \emph{Function Replacement Mode}

\subsubsection{Invocation Listener Mode}
Using this mode, the developer only needs to specify the \texttt{on\_enter} (injected logic before the original function) and \texttt{on\_leave} (injected logic after the original function), without worrying about defining strict C++ function signatures, since Frida-Gum wraps the captured \texttt{GumCpuContext} inside a high-level \texttt{GumInvocationContext} handle passed to user callbacks. In this way arguments and return values can be accessed and modified dynamically by their index, regardless of the target process architecture.

The Frida-Gum Invocation Listener implementation for intercepting \texttt{MessageBoxW} is illustrated in \cref{lst:frida}.

\begin{lstlisting}[language=C, caption={Frida-Gum Invocation Listener mode (\texttt{on\_enter}/\texttt{on\_leave}) for \texttt{MessageBoxW}.}, label={lst:frida}, basicstyle=\ttfamily\footnotesize, breaklines=true]
	// Pre-execution callback
	static void
	example_listener_on_enter (GumInvocationContext * ic, gpointer user_data)
	{
		// Arguments accessed by index: 0:hWnd, 1:lpText, 2:lpCaption, 3:uType
		guint modifiedType = MB_YESNO;
		static const wchar_t* customCaption = L"Hooked, choose:";
		
		gum_invocation_context_replace_nth_argument (ic, 2, (gpointer) customCaption);
		gum_invocation_context_replace_nth_argument (ic, 3, GUINT_TO_POINTER (modifiedType));
	}
	
	// Post-execution callback
	static void
	example_listener_on_leave (GumInvocationContext * ic, gpointer user_data)
	{
		int result = GPOINTER_TO_INT (gum_invocation_context_get_return_value (ic));
		if (result == IDNO) 
		{
			g_print ("Intercepted IDNO. Changing result to IDYES\n");
			gum_invocation_context_replace_return_value (ic, GINT_TO_POINTER (IDYES));
		}
	}
\end{lstlisting}

While Invocation Listener Mode offers architecture abstraction, it introduces a limitation under specific calling conventions (such as the Windows x86/x64 \ac{ABI}): since the API for accessing arguments  (\texttt{gum\_invocation\_context\_get\_nth\_argument}) index exclusively into General-Purpose Registers (\texttt{RCX}, \texttt{RDX}, \texttt{R8}, \texttt{R9}), parameter extraction fails for functions receiving floating-point values, which are passed via vector registers.

\subsubsection{Function Replacement Mode}
\label{subsec:frida_modes}

To overcome the limitations of index-based parameter extraction and achieve parity with traditional frameworks, Frida-Gum exposes \emph{Function Replacement Mode} via \texttt{gum\_interceptor\_replace} and \texttt{gum\_interceptor\_replace\_fast}.

\begin{enumerate}
	\item \textbf{Standard Replacement (\texttt{gum\_interceptor\_replace}):} Execution passes through Frida-Gum's \texttt{enter\_thunk}, where \texttt{GumCpuContext} captures the CPU state and triggers the dispatcher (identical to Invocation Listener Mode). However, instead of invoking high-level callback listeners and then jumping to the original function, the dispatcher redirects execution to a user-defined replacement function—acting as a standard C/C++ detour payload similar to Detours or MinHook (also here strict ABI compliance must be ensured). Crucially, all CPU registers are restored prior to entering the replacement function, allowing the C/C++ compiler to handle float parameters passing natively via standard C signatures.
	\item \textbf{Fast Replacement (\texttt{gum\_interceptor\_replace\_fast}):} Emits a direct assembly \texttt{JMP} instruction from the target prologue straight to the replacement function, bypassing Frida-Gum's dispatcher creation entirely, yielding an execution flow identical to traditional frameworks like Detours and MinHook.
\end{enumerate}

The equivalent Function Replacement implementation for \texttt{MessageBoxW} is illustrated in \cref{lst:frida_replace}.

\begin{lstlisting}[language=C++, caption={Frida-Gum Function Replacement mode using native C/C++ prototypes.}, label={lst:frida_replace}, basicstyle=\ttfamily\footnotesize, breaklines=true]
	// Function pointer type definition matching target signature
	typedef int (WINAPI * TrueMessageBoxW_t)(HWND hWnd, LPCWSTR lpText, LPCWSTR lpCaption, UINT uType);
	static TrueMessageBoxW_t TrueMessageBoxW = NULL;

	// C++ Detour Function
	int WINAPI HookedMessageBoxW(HWND hWnd, LPCWSTR lpText, LPCWSTR lpCaption, UINT uType)
	{
		static const wchar_t* customCaption = L"Hooked, choose:";
		UINT modifiedType = MB_YESNO;

		// Call original implementation via trampoline
		int result = TrueMessageBoxW(hWnd, lpText, customCaption, modifiedType);

		if (result == IDNO)
			result = IDYES;

		return result;
	}

	// Attachment via Standard Replacement Mode
	gum_interceptor_replace(interceptor,
		GSIZE_TO_POINTER(gum_module_find_export_by_name(NULL, "MessageBoxW")),
		(gpointer)HookedMessageBoxW,
		NULL,
		(gpointer*)&TrueMessageBoxW);
	
	// or Attachment via Fast Replacement Mode
	gum_interceptor_replace_fast(interceptor,
		GSIZE_TO_POINTER(gum_module_find_export_by_name(NULL, "MessageBoxW")),
		(gpointer)HookedMessageBoxW,
		(gpointer*)&TrueMessageBoxW);
	
	
	
\end{lstlisting}

\subsection{Execution Flow}
\label{subsec:hook_dispatch}

While all the presented frameworks utilize inline prologue patching, the role of the engine during the detour execution flow differs:

\begin{itemize}
	\item \textbf{Passive Dispatch (Detours, MinHook, Frida Fast Replacement):} Overwrites the target prologue with a direct assembly jump (\texttt{JMP}) to the injected payload. The engine acts purely as a passive observer, delegating all execution routing and state management entirely to the user-written detour function.
	
	\item \textbf{Active Dispatch (Frida Invocation Listener Mode):} Execution jumps into a framework-managed dispatcher. It automatically dispatches CPU register serialization (\texttt{GumCpuContext}), and optional user-defined callbacks before transferring control to the target function.
	
	\item \textbf{Hybrid Dispatch (Frida Standard Replacement Mode):} Combines dispatcher with user-controlled execution routing. The engine intercepts execution via its dispatcher, but then yields execution control to a user-defined replacement function. The replacement function acts as an autonomous detour function, with the same structure seen in passive dispatch frameworks.
\end{itemize}

\subsubsection{Advantages of Engine-Mediated Dispatch}
\label{subsubsec:advantages}

Frida-Gum employs a framework dispatcher in both Invocation Listener (active) and Standard Replacement (hybrid) modes to deliver useful capabilities that traditional frameworks do not automatically provide:

\begin{enumerate}
	\item \textbf{Multi-Listener Hook (Active dispatch):} With Detours or MinHook, developers are forced to manage fragile, nested chains of function pointers when multiple hooks target the same function. In contrast, Frida-Gum's active dispatcher maintains an internal list of subscribers (\texttt{listener\_entries}) inside target related internal structure \texttt{GumFunctionContext}. The active dispatcher sequentially invokes the \texttt{on\_enter} and \texttt{on\_leave} callbacks of all attached listeners (e.g., logging, security monitoring) in a single execution pass without requiring individual listeners to be aware of one another.
	
	\item \textbf{Built-in Thread Tracking for Safe Detachment (\texttt{gum\_interceptor\_flush}):} The framework dispatcher automatically maintains an internal thread counter inside \texttt{GumFunctionContext}, incrementing it upon entry (\texttt{enter\_thunk}) and decrementing it upon completion (\texttt{leave\_thunk}). This provides native support for safe framework detachment \cref{subsec:ejection_sync}.
	
	\item \textbf{Automatic CPU State Preservation:} In traditional hooking, register preservation relies entirely on compiler-generated instructions matching the exact target ABI; any convention mismatch risks register corruption and crashes. In contrast, Frida-Gum's active dispatcher automatically serializes all CPU hardware registers into an architecture-agnostic \texttt{GumCpuContext} structure upon entry and restores them upon exit. Exposed to callbacks via \texttt{gum\_invocation\_context\_get\_cpu\_context(ic)}, this mechanism guarantees process state integrity across supported architectures while allowing developers to safely inspect or modify General-Purpose Registers dynamically at runtime.
	
	\item \textbf{Automatic Recursion and Re-entrancy Protection:} When instrumenting low-level runtime routines (e.g., \texttt{malloc}, \texttt{open}, \texttt{write}, or \texttt{memcpy}), the user-defined hook payload or dependencies (such as logging frameworks, string formatters, or heap allocators) frequently invoke the hooked function internally. Under passive dispatch (e.g., Detours, MinHook) or Frida's fast replacement mode (\texttt{gum\_interceptor\_replace\_fast}), calling the target function without explicitly routing through an unhooked trampoline pointer triggers unbounded recursion, immediately terminating the application with a stack overflow. In contrast, Frida-Gum's standard replacement dispatcher maintain a per-thread \ac{TLS} re-entrancy guard. If the dispatcher detects that the calling thread is already executing inside the replacement scope for that target, it automatically bypasses the hook and vectors execution directly through the original routine via \texttt{on\_invoke\_trampoline}, effectively preventing recursive deadlock and stack exhaustion.
\end{enumerate}

\subsubsection{Trade-offs and the Fast Replacement Bypass}

Despite their capabilities, active and hybrid dispatch introduce a non-trivial performance trade-off. Execution through the framework's centralized dispatcher (\texttt{enter\_thunk}) requires allocating memory for context structures and executing multiple CPU register serializations on every function invocation. For high-frequency target routines executed millions of times per second (e.g., memory allocations or critical section acquisitions), this additional CPU overhead can degrade execution speed compared to  passive jumps.

This latency penalty explains the primary role of Frida-Gum's \emph{Fast Replacement Mode} (\texttt{gum\_interceptor\_replace\_fast}). By emitting a raw assembly \texttt{JMP} instruction directly from the target prologue to the replacement payload, fast replacement bypasses the \texttt{enter\_thunk} dispatcher and \texttt{GumCpuContext} creation entirely. This design trades all the previously presented advantages of using an intermediate dispatcher for minimal hook latency.

\subsection{Instruction Boundaries and the Role of Disassemblers}

\note{Advisor}{cyan}{Non so se mettere questa sezione}
A fundamental challenge in implementing the hook structure described above, particularly on Intel x86 and x64 architectures, is the variable-length nature of the instruction set.
To detour a target function, an inline hooking framework typically needs to overwrite the first few bytes of the function's prologue with an unconditional jump (\texttt{JMP}) to the custom payload.
In a standard 32-bit architecture, this jump requires 5 bytes (1 byte for the opcode, 4 bytes for the relative address).
If the framework blindly overwrites exactly 5 bytes, it risks cutting an existing instruction in half.
If the original prologue consists of two 3-byte instructions, overwriting 5 bytes will corrupt the second instruction, leaving a hanging, invalid byte.
When the trampoline attempts to execute these copied bytes to resume the program, the CPU will encounter an invalid opcode and crash the process.
To prevent this, hooking frameworks must incorporate a Length Disassembler Engine (LDE).
Before applying any patches, the engine disassembles the target function's prologue to calculate exact instruction boundaries.
It then copies whole, unfragmented instructions into the trampoline until it has safely relocated at least the number of bytes required for the jump (padding any remaining bytes in the original function with \texttt{NOP} instructions).
The choice of disassembler heavily impacts the footprint and dependencies of the framework:
\begin{itemize}
	\item \emph{Microsoft Detours} relies on a proprietary, internal instruction decoder optimized specifically for standard compiler prologues.
	\item \emph{MinHook} utilizes a highly optimized, custom-built Hacker Disassembler Engine \allowbreak (HDE32/\allowbreak HDE64) to calculate instruction lengths, rather than fully analyze instruction semantics.
	\item \emph{Frida-Gum} requires deep semantic analysis of the instructions to achieve its context-aware routing.
	To accomplish this, it statically links against Capstone, a comprehensive and heavy multi-architecture disassembly framework, significantly increasing the size of the resulting \ac{DLL}.
\end{itemize}

\subsection{Transactional Patching}
\label{subsec:transactional_patching}

A critical challenge in inline hooking is applying the memory patch (the \texttt{JMP} instruction) to a live, executing process without inducing a \emph{race condition}.

In a multi-threaded application, if a worker thread attempts to execute a target function's prologue at the exact instant the instrumentation framework is overwriting its bytes, the CPU may decode a partially written, invalid opcode, triggering an immediate process crash.
To prevent this, instrumentation frameworks implement a \emph{transactional model}.
However, the concrete mechanism used to guarantee concurrency safety diverges significantly depending on the design of the engine.
The presented frameworks fall into two paradigms: \emph{Pessimistic Relocation} and \emph{Non-Blocking Batching}.

\subsubsection{Thread Enlistment and IP Relocation}

Frameworks tailored natively for Windows, such as \emph{Microsoft Detours} and \emph{MinHook}, follow a pessimistic synchronization model.
Before modifying target memory, concurrent worker threads are temporarily suspended to prevent race conditions during prologue patching.
However, the scope of thread suspension differs fundamentally between the two engines: while \emph{Detours} requires the developer to explicitly enlist target thread handles, \emph{MinHook} automatically captures a process-wide thread snapshot to suspend all running worker threads.

Crucially, simply suspending threads is insufficient on its own.
A worker thread might have been preempted at the exact moment its Instruction Pointer (\ac{IP}, i.e., \texttt{EIP}/\texttt{RIP}) was positioned within the byte range of the prologue being overwritten.
If resumed naively, the thread would execute the newly written destination address of the detour jump as raw machine code, corrupting execution.
To prevent this, the framework inspects the register context of each suspended thread (\texttt{GetThreadContext}).
If a thread's \ac{IP} falls within the replaced address range, the framework dynamically adjusts the \ac{IP} to point to the corresponding relocated instruction inside the trampoline (when attaching) or back to the restored prologue bytes (when detaching).

\emph{Microsoft Detours} makes this transaction explicitly developer-managed.
The developer begins a transaction, explicitly enumerates and enlists every thread via \texttt{DetourUpdateThread}, queues the hook attachments or detachments, and commits the transaction, as illustrated in \cref{lst:detours_lifecycle}.
During \texttt{DetourTransactionCommit}, Detours suspends the enlisted threads, verifies and relocates their instruction pointers, applies the patches, flushes the CPU instruction cache, and resumes execution.

\begin{lstlisting}[language=C++, caption={Microsoft Detours transactional model with explicit thread enlistment and IP relocation.}, label={lst:detours_lifecycle}, basicstyle=\ttfamily\footnotesize, breaklines=true]
	// ATTACHMENT
	
	// Start the transaction
	DetourTransactionBegin();
	
	// Enlist threads whose instruction pointers must be inspected and relocated
	DetourUpdateThread(GetCurrentThread()); 
	for (HANDLE hThread : workerThreads) {
	    DetourUpdateThread(hThread);
	}
	
	// Queue the hook attachments
	DetourAttach(&(PVOID&)TrueMessageBoxW, HookedMessageBoxW);
	
	// Atomically suspend enlisted threads, rewrite IPs, patch bytes, and resume
	DetourTransactionCommit();
	
	// DETACHMENT
	DetourTransactionBegin();
	
	DetourUpdateThread(GetCurrentThread());
	// here we specify possible other threads we want to be inspected...
	
	DetourDetach(&(PVOID&)TrueMessageBoxW, HookedMessageBoxW);
	// here we specify possible other hooks we want to detach...
	
	// Atomically suspend threads, restore prologue bytes, fixup IPs, and resume
	DetourTransactionCommit();
\end{lstlisting}

\emph{MinHook} adopts the exact same underlying mechanism but abstracts the transaction boundaries from the public API (\cref{lst:minhook_lifecycle}).
Internally, when \texttt{MH\_EnableHook} or \texttt{MH\_DisableHook} is invoked, the library enumerates process threads via a Toolhelp32 snapshot, suspends them, performs instruction-pointer relocation, applies the patch, and resumes the threads.

\begin{lstlisting}[language=C++, caption={MinHook internal thread synchronization during enable/disable phases.}, label={lst:minhook_lifecycle}, basicstyle=\ttfamily\footnotesize, breaklines=true]
	// ---  ATTACHMENT ---
	MH_CreateHook(&MessageBoxW, &HookedMessageBoxW, reinterpret_cast<LPVOID*>(&fpMessageBoxW));
	
	// MH_EnableHook internally captures snapshots, suspends threads, rewrites IPs, and resumes
	MH_EnableHook(&MessageBoxW);
	//or MH_EnableHook(MH_ALL_HOOKS); if we have more than one hook
	
	// ---  DETACHMENT ---
	// MH_DisableHook internally suspends threads, restores original bytes, rewrites IPs, and resumes
	MH_DisableHook(&MessageBoxW);
	//or MH_DisableHook(MH_ALL_HOOKS); if we have more than one hook
\end{lstlisting}

\subsubsection{Non-Blocking Batching}

In contrast to Detours and MinHook, \emph{Frida-Gum} was designed as a cross-platform instrumentation runtime.
In cross-platform environments, suspending all running threads across a process is either not exposed by operating system primitives or heavily restricted by sandboxing.

Consequently, Frida-Gum does \emph{not} implement thread enlisting, process-wide thread suspension, or register context inspection during hook installation.
Instead, Frida-Gum's transactional API (\texttt{gum\_interceptor\_begin\_transaction} and \texttt{gum\_interceptor\_end\_transaction}) serves as a \emph{staging and batching boundary} for applying patches in an efficient way but not for atomicity purpose, as shown in \cref{lst:frida_lifecycle}:


\begin{lstlisting}[language=C++, caption={Frida-Gum transactional lifecycle for staged, batched function replacement.}, label={lst:frida_lifecycle}, basicstyle=\ttfamily\footnotesize, breaklines=true]
	// ---  ATTACHMENT ---
	gum_interceptor_begin_transaction(interceptor);
	
	// Function Replacement Mode
	gum_interceptor_replace(interceptor, target_func, (gpointer)HookedFunc, NULL, (gpointer*)&TrueFunc);
	// OR 
	gum_interceptor_replace_fast(...)
	
	// OR Invocation Listener Mode 
	// gum_interceptor_attach(interceptor, target_func, listener, NULL, GUM_ATTACH_FLAGS_NONE);

	gum_interceptor_end_transaction(interceptor);

	// ---  DETACHMENT ---
	gum_interceptor_begin_transaction(interceptor);
	
	// Revert target prologue bytes
	gum_interceptor_revert(interceptor, target_func);
	
	// OR Invocation Listener Mode
	// gum_interceptor_detach(interceptor, listener);

	gum_interceptor_end_transaction(interceptor);
\end{lstlisting}

\subsection{Thread-Safe Ejection}
\label{subsec:ejection_sync}

During the \emph{detachment phase}, restoring the target function's original prologue bytes prevents \emph{new} executions from entering the hook payload. However, transactional byte restoration alone is insufficient to guarantee safe \ac{DLL} ejection (\texttt{FreeLibrary}). In multi-threaded applications, worker threads may already be executing inside the custom detour logic when prologue reversion occurs. If the host process unmaps the instrumentation \ac{DLL} memory while a worker thread is active inside the hook logic, the thread encounters unmapped virtual memory, triggering an immediate Access Violation (\texttt{0xC0000005}).

To achieve thread-safe ejection, inline hooking architectures must supplement transactional byte restoration with a \emph{Synchronization mechanism}. As illustrated in \cref{lst:ejection_sync}, two distinct approaches can be used to achieve safety ejection:
\begin{enumerate}
	\item \textbf{Manual Tracking:} Because Detours and MinHook have no internal thread awareness, the instrumentation wrapper must wrap each detour function in a guard that atomically increments a global counter upon entry and decrements it upon exit. During detachment, after committing the prologue restoration transaction, the payload spin-waits until the counter reaches zero.
	\item \textbf{Built-in Tracking:} Because Frida-Gum's active dispatcher automatically tracks active threads across \texttt{enter\_thunk} and \texttt{leave\_thunk} (\cref{subsubsec:advantages}), it exposes a native flushing API. During detachment, after reverting patches, \texttt{gum\_interceptor\_flush()} is called in a spin-wait loop, it returns \texttt{TRUE} only when all in-flight threads have completely finished.
\end{enumerate}

\begin{lstlisting}[language=C++, caption={synchronization protocols for thread-safe module ejection in Detours and Frida-Gum.}, label={lst:ejection_sync}, basicstyle=\ttfamily\footnotesize, breaklines=true]
// =========================================================================
// Detours / MinHook
// =========================================================================
static std::atomic<int> g_activeHooks{0};
struct HookGuard {
    HookGuard()  { g_activeHooks++; }
    ~HookGuard() { g_activeHooks--; }
};
void HookedProcessTask(int taskId, const char* taskType, int complexity) {
    HookGuard guard; // Automatically tracks thread execution scope
    // Custom detour logic...
    TrueProcessTask(taskId, taskType, complexity);
}
void SafeDetach_Detours() {
    // 1: Revert prologue bytes via transactional patch
    DetourTransactionBegin();
    // ...

    // 2:  wait for in-flight threads to exit
    while (g_activeHooks.load() > 0) {
        SwitchToThread();
    }
}
// =========================================================================
// Frida-Gum
// =========================================================================
void SafeDetach_Frida(GumInterceptor* interceptor, gpointer target_func) {
    // 1: Revert prologue bytes via transactional patch
    gum_interceptor_begin_transaction(interceptor);
    // ...
    
    // 2: wait for active dispatcher signal to flush
    while (!gum_interceptor_flush(interceptor)) {
        SwitchToThread();
    }
}
\end{lstlisting}

\section{Code-Cache Based DBI}
\label{sec:code_cache_dbi}

For deeper execution analysis at the assembly level, code-cache-based \ac{DBI} engines are utilized.
Unlike inline hooking, which patches the original binary in place, code-cache-based \ac{DBI} engines ensure that the target application's original code is never executed directly by the CPU.
Instead, the framework employs a \emph{Just-In-Time (JIT) compilation} mechanism to dynamically translate and instrument instruction sequences.
\subsection{Core Architectural Components}
Modern code-cache-based \ac{DBI} frameworks rely on a unified architectural pattern comprising the following components:

\begin{description}
	\item[1. The Dispatcher (Control Flow Manager):] The dispatcher is the central component of the code-cache \ac{DBI} engine, responsible for orchestrating the execution state.
	Because the application and the code-cache \ac{DBI} framework share the same process but operate under different scopes, they must safely transit between ``framework mode'' and ``application mode''.
	The dispatcher triggers a context-switch mechanism that carefully saves and restores the application's state whenever execution exits or enters the code cache.
	\item[2. \ac{JIT} Compiler:] Instead of translating the entire binary before execution, these architectures translate the application's instructions dynamically in small fragments.
	During this translation phase, the framework decodes and encodes (into the framework's abstraction) the original instructions and has the opportunity to insert custom instrumentation code or patches before emitting the new sequence.
	\item[3. The Code Cache (The Execution Sandbox):] To mitigate the massive performance penalty of repeatedly translating the same code, code-cache-based \ac{DBI} frameworks employ a software-based code cache.
	The translated and potentially instrumented fragments are stored in this sandboxed memory region.
	When the application re-executes a previously translated section of code, it runs directly from the code cache, which significantly optimizes execution speed.
	\item[4. The Client Interface (Instrumentation API):] This is the abstraction layer exposed to the developer.
	It provides the necessary functions to inspect the program state, traverse instruction sequences, and specify exactly where and how instrumentation should be injected.
\end{description}

\subsection{The Execution Lifecycle: The JIT Loop}
To formally describe how these components interact at runtime, we can outline the execution lifecycle of a standard block of code, illustrated in \cref{fig:dbi_flow}:

\begin{enumerate}
	\item \emph{Interception:} The target application attempts to execute a block of original code.
	The code-cache \ac{DBI} engine intercepts this attempt and yields control to the Dispatcher.
	\item \emph{Cache Lookup:} The Dispatcher queries a fast-lookup hash table to check if the target memory address has already been translated.
	If it results in a cache hit, the CPU is redirected to the Code Cache.
	\item \emph{Translation (On Cache Miss):} If the code has not been encountered before, the \ac{JIT} Compiler decodes original binary instructions one by one to form a straight-line sequence that terminates at a control transfer, such as a branch, call, or return.
	\item \emph{Instrumentation:} The engine queries the Client Interface to determine if the user wishes to instrument the block or a single instruction within it.
	If so, the instrumentation instructions are injected. 
	\item \emph{Emission and Linking:} Most code-cache-based \ac{DBI} frameworks use this phase to apply patches to the control-flow instructions at the end of the sequence, guaranteeing that when the block finishes running, it will redirect back to the framework rather than jumping to a native memory address.
	If the block ends in a direct branch to another previously translated block, the engine ``links'' them together directly in the cache (if it was an indirect branch, it cannot know the target before executing it), allowing the CPU to bypass the Dispatcher in future iterations.
	The modified block is emitted into the Code Cache.
	\item \emph{Execution:} The Dispatcher performs a context switch, restoring the application state, and commands the CPU to execute the newly cached block natively.
	\item \emph{Code Cache Exit:} Execution remains safely inside the code cache --- often jumping directly from one translated block to another through ``linking''---until it hits a boundary.
	This boundary might be an unlinked branch or an indirect branch whose target hasn't been translated yet.
	When this happens, the block executes an exit stub which saves the CPU's state and transfers control back to the Dispatcher, restarting the loop.
\end{enumerate}

\begin{figure}[H]
	\centering
	\includegraphics[width=0.9\textwidth]{images/DBI_flow.png}
	\caption{The Execution Lifecycle of a Code-Cache-Based DBI framework}
	\label{fig:dbi_flow}
\end{figure}

While code-cache-based \ac{DBI} frameworks allow a more granular analysis of the target code, they introduce \emph{significantly higher overhead} compared to inline hooking.
Every single instruction of the program needs to be \ac{JIT}-compiled before execution, even if no instrumentation is injected.
\subsection{The Client Interface: Instrumentation vs. Analysis Functions}

Code-cache-based \ac{DBI} frameworks require the developer to interact with the engine using a \emph{two-tiered callback paradigm}.
The developer must supply two distinct types of functions to the engine, each operating at fundamentally different times during the execution lifecycle:

\begin{itemize}
	\item \emph{The Instrumentation Function (The ``Where'' and ``What''):} 
	This callback is invoked by the code-cache \ac{DBI} engine \emph{only once} per newly discovered sequence of instructions during the \ac{JIT} compilation phase.
	Its purpose is to inspect the static properties of the instructions (e.g., opcodes, operands) and decide \emph{if} and \emph{where} custom code should be injected.
	If injection is required, it uses the \ac{API} to queue the insertion of the analysis function.
	\item \emph{The Analysis Function (The ``Action''):} 
	This is the actual custom payload injected into the Code Cache.
	Unlike the instrumentation function (executed only at compile time), it is executed \emph{every time} the CPU runs the corresponding instrumented block of code.
	For this reason, the analysis function must be heavily optimized and efficient.
\end{itemize}

The level of abstraction provided by the Client Interface significantly alters how developers interact with the engine.
\subsection{High-Level Abstraction API: Intel PIN}
Intel PIN~\cite{DBLP:conf/pldi/LukCMPKLWRH05} is a standard academic code-cache-based \ac{DBI} framework with a proprietary (free for non-commercial use) license.
It provides a heavily abstracted C++ \ac{API}.

To utilize Intel PIN, developers do not modify the core engine itself.
Instead, they write a custom C++ program known as a \emph{PINtool}.
A PINtool represents the physical implementation of the Client Interface discussed previously;
it is the user-defined module that contains both the Instrumentation Functions and the Analysis Functions.
Architecturally, a PINtool is compiled as a standard shared library (a \ac{DLL} on Windows).
When the user launches a target application under PIN, the engine automatically injects the PINtool \ac{DLL} into the target process's memory space.
Once loaded, the engine invokes the PINtool's \texttt{main} function, allowing the tool to register its specific callbacks.
In \cref{lst:pin_branch}, we can observe the granularity achievable using code-cache-based \ac{DBI}: in this case, we can log conditional branches to determine which paths are taken during code execution.


\begin{lstlisting}[language=C++, caption={An example of a PINtool for branch logging}, label={lst:pin_branch}, basicstyle=\ttfamily\footnotesize, breaklines=true]
	// Analysis function (Runs at execution time in the Code Cache)
	void record_branch(ADDRINT instruction_address, ADDRINT target_address, BOOL taken) {
		
		if (taken) { /* Log Taken */ } 
		else       { /* Log Not Taken */ }
	}
	
	// Instrumentation function (Runs at JIT compilation time)
	void trace(INS instruction, void *v) {
		
		// PIN abstracts away module resolution: we want to instrument
		// only target application instructions, filter possible external libraries
		RTN rtn = INS_Rtn(instruction);
		if (RTN_Valid(rtn) && IMG_IsMainExecutable(SEC_Img(RTN_Sec(rtn)))) {
			// If it is inside the target executable, check if it's an IF branch
			if (INS_IsBranch(instruction) && INS_HasFallThrough(instruction)) {
				// Inject analysis function right before the jump happens.
				INS_InsertCall(instruction, IPOINT_BEFORE, (AFUNPTR)record_branch,
				IARG_INST_PTR,           
				IARG_BRANCH_TARGET_ADDR,  
				IARG_BRANCH_TAKEN,        
				IARG_END);
			}
		}
	}
\end{lstlisting}

\subsection{low-level API: DynamoRIO}
DynamoRIO~\cite{DBLP:conf/cgo/BrueningGA03} is the open-source alternative that exposes a lower-level C \ac{API}.
The equivalent branch-logging example seen previously for PIN is implemented in \cref{lst:dr_branch}.

\begin{lstlisting}[language=C, caption={DynamoRIO branch instrumentation example}, label={lst:dr_branch}, basicstyle=\ttfamily\footnotesize, breaklines=true]
	// Analysis function
	static void record_branch(app_pc instr_addr, app_pc target_addr, int taken) {
		
		if (taken) { /* Log Taken */ } 
		else       { /* Log Not Taken */ }
	}
	
	// Instrumentation function
	static dr_emit_flags_t event_bb_analysis(void *drcontext, void *tag, instrlist_t *bb, instr_t *inst, bool for_trace, bool translating,
	void *user_data) {
		
		// Manual module tracking to filter out OS libraries
		app_pc instr_addr = instr_get_app_pc(inst);
		module_data_t *mod = dr_lookup_module(instr_addr);
		bool is_main_exec = false;
		
		if (mod != NULL) {
			module_data_t *main_mod = dr_get_main_module();
			if (main_mod != NULL) {
				if (mod->start == main_mod->start) { is_main_exec = true;
				}
				dr_free_module_data(main_mod);
			}
			dr_free_module_data(mod);
		}
		
		if (!is_main_exec) return DR_EMIT_DEFAULT;
		// Check if it's a conditional branch (CBR)
		if (instr_is_cbr(inst)) {
			// Inject analysis function into the basic block (bb)
			dr_insert_cbr_instrumentation(drcontext, bb, inst, (void *)record_branch);
		}
		return DR_EMIT_DEFAULT;
	}
\end{lstlisting}

Using DynamoRIO, developers can directly manipulate the instruction flow.
In PIN, developers generally ``wrap'' existing instructions (adding a call before or after an instruction) but cannot easily modify the instruction itself. 
In DynamoRIO, the developer is handed a linked list of instructions (\texttt{instrlist\_t}) and can easily manipulate or modify them (e.g., reordering them or moving a load instruction earlier to test for race condition).

Furthermore, because PIN is designed to be highly opaque, using \texttt{INS\_InsertCall} prompts PIN's \ac{JIT} compiler to automatically analyze the custom analysis function for deciding which registers need to be saved and restored based on what the C++ code actually uses. 
With DynamoRIO, developers can manage the 
state and flags manually for specialized analysis.

In conclusion, while DynamoRIO may present a steeper learning curve than Intel PIN, it affords developers greater transparency and raw power, providing fine-grained control over the translated code and the code cache.

\section{Experimental Validation}
\label{sec:experimental_validation}

To empirically validate the theoretical concepts discussed in the preceding sections and to fully understand the operational constraints, security boundaries, and low-level deployment challenges of each framework, a propedeutic suite of testing applications was developed. All source code and custom injection utilities have been organized and made available within the project's repository.\footnote{\url{https://github.com/davde342/MasterThesis/tree/main/code/first_examples}} 

The experimental activity was structured into three different scenarios, each designed to evaluate specific architectural properties of the instrumentation engines.

\subsection{Scenario 1: Single-Threaded Hooking and Process Injection/Ejection Mechanics}
\label{subsec:scenario_1}

\begin{itemize}
	\item \textbf{Test Rationale:} This preliminary scenario aimed to verify the fundamental lifecycle management of \ac{DBI} within the Windows ecosystem. 
	
	This involved implementing a custom, dual-mode utility (\texttt{injector.cpp}) to handle both the insertion and the ejection of the instrumentation payload. 
	
	Concurrently, the test evaluated the syntactic and structural paradigms of the three inline hooking frameworks (Microsoft Detours, MinHook, and Frida-Gum) when intercepting a standard system API—\texttt{MessageBoxW} in \texttt{user32.dll}.
	
	\item \textbf{Empirical Results:} Every analyzed framework successfully intercepted the execution flow during the ``Pre-Logic'' phase. This capability allowed for the modification of string pointers targeting the dialog box text and caption, the reassignment of the configuration flags to \texttt{MB\_YESNO}, and the runtime mutation of the return value during the ``Post-Logic'' phase, effectively forcing an \texttt{IDYES} outcome regardless of the user's explicit interaction. 
	
	Furthermore, forcing the programmatic module ejection successfully triggered the \texttt{DLL\_PROCESS\_DETACH} branch within each hook's entry point, safely restoring the original prologue instruction bytes and confirming a flawless ejection in single-threaded environments.
	
	\item \textbf{Encountered Obstacles:} In this idealized single-threaded scenario, no big challenges occurred. Setting up Microsoft Detours was straightforward due to its thoroughly documented APIs, the abundance of reference examples, and a standard paradigm that is conceptually simpler than that of Frida-Gum. 
	
	MinHook demonstrated a similar workflow to Detours but simplified the implementation further by automatically managing transactional patching internally. 
	
	Conversely, approaching Frida-Gum for the first time presented a steeper learning curve; given its more complex architecture, distinct paradigm, and less exhaustive documentation; comprehensively understanding its API behaviors and mapping them to my use case required a direct analysis of the huge and dense codebase within the official Frida repository.
\end{itemize}

\subsection{Scenario 2: Multi-Threaded Hooking and Concurrency Management}
\label{subsec:scenario_2}

\begin{itemize}
	\item \textbf{Test Rationale:} To simulate a realistic production workload and test the instrumentation frameworks under thread concurrency, a multithreaded target engine was used (\texttt{target\_multithread.cpp}). This target utilizes a synchronized task queue where a producer thread continuously queues activities with varying workloads, while three concurrent consumer threads process these tasks in parallel by invoking the exported routines \texttt{ProcessTask} and \texttt{LogTaskResult}.
	
	\item \textbf{Empirical Results:} Real-time monitoring of thread behaviors was achieved, allowing a dynamic optimization policy: the injected hook intercepted high-latency tasks (>500ms) and programmatically constrained their complexity metrics to 100ms prior to native routing, illustrating the possibility of inline hooking for runtime policy enforcement and load adaptation.
	
	\item \textbf{Encountered Obstacles:} Two major obstacles I faced in this scenario. First, performing hook detachment in a concurrent context introduced a possible race condition: active worker threads could be descheduled while executing inside the hook callback, causing an immediate Access Violation (\texttt{0xC0000005}) once the library was unmapped. 
	
	Second, in Frida-Gum, intercepting routines that process floating-point arguments (such as the \texttt{double} parameter in \texttt{LogTaskResult}) encountered an ABI mismatch because these parameters are passed via \texttt{XMM0}--\texttt{XMM3} registers under the Windows x64 ABI, while Frida expects them in other registries.
	
	\item \textbf{Implemented Mitigations:} To address the detachment race condition in concurrent environments, framework-specific synchronization protocols were deployed (as formalized in \cref{subsec:ejection_sync} and \cref{lst:ejection_sync}).	
	
	As detailed in \cref{subsec:frida_arch}, to bypass the floating-point register limitation inherent in Frida-Gum's Invocation Listener mode, the high-level callback attachment was discarded in favor of Frida-Gum's Function Replacement mode via \texttt{gum\_\allowbreak interceptor\_\allowbreak replace}, allowing the C/C++ compiler to handle exact register allocation natively.

\end{itemize}

\subsection{Scenario 3: Instruction-Level Assembly Tracking via Code-Cache-Based DBI Engines}
\label{subsec:scenario_3}

\begin{itemize}
	\item \textbf{Test Rationale:} To achieve low-level instruction granularity, a target program containing conditional branches was compiled (\texttt{PIN\_\allowbreak dynamo\_\allowbreak target.cpp}), alongside an Intel PIN tool (\texttt{pintool.cpp}) and a DynamoRIO client (\texttt{dynamo.c}). The rationale was to program the underlying JIT compilers to isolate all conditional branch instructions (\texttt{INS\_IsBranch} / \texttt{instr\_is\_cbr}) and dynamically inject an analysis callback (\texttt{record\_branch}) used to log the target address (taken branch).
	
	\item \textbf{Empirical Results:} Both code-cache-based \ac{DBI} engines yielded execution trace graphs. Using IntelPIN it was also possible to write the source file code line number correspondent to the taken branch
	
	\item \textbf{Encountered Obstacles:} An initial operational challenge involved navigating the different APIs of the two frameworks; DynamoRIO exposes lower-level, low-level utilities compared to the highly abstracted API of Intel PIN, resulting in a steeper learning curve. Beyond API familiarity, the primary technical obstacle across both engines was attempting to log not only the target runtime address of each taken branch but also its source code line number from \texttt{PIN\_dynamo\_target.cpp} (compiled with debug symbols) to maximize execution trace readability.
	
	\item \textbf{Implemented Mitigations:} After several unsuccessful attempts, I have found that for solving the source line number obstacle under Intel Pin, I had to utilize the \texttt{PIN\_GetSourceLocation} API. However, direct invocation of this routine inside the analysis function triggers a critical runtime error due to missing client locks. To mitigate this, calls to \texttt{PIN\_GetSourceLocation} were wrapped inside a thread-safe synchronization pair using \texttt{PIN\_LockClient()} and \texttt{PIN\_UnlockClient()}, ensuring proper access to Pin's symbol database.
\end{itemize}
