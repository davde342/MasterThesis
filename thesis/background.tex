\chapter{Background}
\label{ch:background}

This chapter begins by introducing the foundational concepts of binary instrumentation within a Windows environment necessary to understand the proposed work.
Subsequently, it analyzes state-of-the-art frameworks utilized for binary instrumentation. This overview is essential for contextualizing the compilation targets selected for our Domain-Specific Language (DSL), which are discussed in detail in \fullref{ch:method}.

As discussed in \fullref{ch:introduction}, binary instrumentation allows us to change the runtime behavior of a binary, injecting a compiled payload into an existing executable.

\section{The Application Binary Interface (ABI)}
\label{sec:abi}

At the foundational level of software execution, ensuring interoperability between distinct compiled modules—regardless of the specific compilers or programming languages used—requires a \emph{standardized low-level interface}.
To allow external code or instrumentation payloads to safely interact with a target process without causing unexpected runtime crashes, the execution flow must strictly adhere to the Application Binary Interface (ABI).
The ABI defines the low-level rules for how functions interact at the assembly level, including how parameters are passed to a function, how return values are retrieved, and which entity is responsible for cleaning up the stack (the caller or the callee).
These rules are formalized as \emph{Calling Conventions}.
The complexity of ABI compliance and the risk of runtime crashes depend heavily on the target architecture.

\subsection*{Windows x86 (32-bit) Architecture}
In 32-bit environments, multiple calling conventions coexist, requiring developer-level alignment between the instrumentation target function and the injected payload implementation.
The most common conventions include:
\begin{itemize}
	\item \texttt{\_\_cdecl}: Arguments are pushed onto the stack from right to left, and the \emph{caller} cleans the stack.
	This is the default convention for C/C++ binaries.
	\item \texttt{\_\_stdcall}: The standard convention for the Windows \ac{API}.
	Arguments are pushed right to left, but the \emph{callee} cleans the stack.
	\item \texttt{\_\_fastcall}: The first two arguments are passed in the \texttt{ECX} and \texttt{EDX} registers for speed, while the rest are placed on the stack.
\end{itemize}
Understanding and matching these different conventions is critical for binary instrumentation on x86.

\subsection*{Windows x64 (64-bit) Architecture}
To eliminate the complexity of managing multiple incompatible conventions, Windows x64 introduces a single, unified calling convention (a standard x64 ABI).
In this environment, legacy keywords like \texttt{\_\_cdecl}, \texttt{\_\_stdcall}, and \texttt{\_\_fastcall} are accepted by the compiler for backward compatibility but are syntactically ignored.
The x64 calling convention utilizes a register-based parameter passing scheme:
\begin{itemize}
	\item The first four integer or pointer arguments are passed from left to right in registers (\texttt{RCX}, \texttt{RDX}, \texttt{R8}, and \texttt{R9}).
	\item The first four floating-point arguments are passed in the \texttt{XMM0}--\texttt{XMM3} registers.
	\item Any arguments beyond the first four are pushed onto the stack.
	\item The caller is always responsible for stack cleanup.
\end{itemize}
From the perspective of binary instrumentation, the single-ABI model of x64 provides an inherent safety net: because the compiler forces both the target process and the injected payload to use the exact same assembly-level rules, calling convention mismatches are impossible.
However, when writing portable instrumentation code intended to be compiled for both architectures, developers must still explicitly specify calling conventions (e.g., using macros like \texttt{WINAPI}) to prevent stack corruption when the codebase is built for x86 targets.

\section{Foundations of Dynamic-Link Libraries}
\label{sec:dll_foundations}

To achieve binary instrumentation in modern Windows environments, we must overcome also some operating system constraints.
Since every process operates within its own isolated virtual address space, a standard process cannot directly read or write the memory of another process.
Therefore, to perform binary instrumentation, we must first find a way to inject and execute our custom instrumentation payload within the context (and memory space) of the target process.

In modern computing environments, executable code can be bound to an application using one of two primary paradigms: static linking or dynamic linking.
\subsection{Static vs. Dynamic Linking}
Under the \emph{static linking model}, any function or external resource required by an application is permanently integrated into the final binary executable (EXE) file at link time.
The linker copies the precompiled object code directly from a static library file into the body of the target program.
While this ensures that the application is fully self-contained, it introduces severe inefficiencies if multiple programs require the same helper functions: each separate program must contain its own physical copy of the code on disk, and each program will load a redundant copy into physical RAM upon execution.

\emph{Dynamic linking} instead defers the binding of external library functions until runtime.
A \ac{DLL} is an independent binary executable module that contains functions, resources, and data that can be called dynamically by other modules or applications.
Rather than duplicating library code inside the host application, the operating system keeps the library code in a separate, isolated file and maps it dynamically to the calling processes as needed, drastically reducing both disk footprint and memory consumption.

\subsection{Memory Mapping and Address Space Isolation}
In modern operating systems, every running application is allocated an isolated, private virtual address space known as a process space.
This architecture strictly prevents one application from directly reading, modifying, or corrupting the code or memory space of another.
To enable resource sharing without violating this isolation boundaries, the operating system utilizes a technique known as virtual memory mapping.
When an application loads a \ac{DLL}, the operating system loader maps the linear address range of the compiled \ac{DLL} binary directly into the virtual address space of the loading process.
Once this mapping is completed, the functions inside the \ac{DLL} behave exactly as if they were natively compiled parts of the host application, gaining the ability to execute within its context and interact directly with its data parameters.

\section{DLLs in Binary Instrumentation}

As discussed in \cref{sec:dll_foundations}, \acp{DLL} are traditionally used to share code libraries across multiple applications, but they possess also specific characteristics that make them the standard vehicle for Windows instrumentation:
\begin{enumerate}
	\item \emph{Automatic Initialization:} When a \ac{DLL} is successfully loaded, the Windows \ac{OS} loader automatically invokes its entry point function, \texttt{DllMain}.
	This allows the instrumentation framework to immediately execute its initialization sequence without requiring the host process to explicitly call any functions.
	\item \emph{Automatic Cleaning:} If the \ac{DLL} is unloaded but the instrumentation code remains active in memory, subsequent executions will jump to an unmapped memory region, triggering an access violation.
	To ensure proper cleanup, when a \ac{DLL} is successfully unloaded, the Windows \ac{OS} loader automatically invokes its entry point function to execute the detachment logic.
	
	\Cref{lst:dllMain} presents the template code for an instrumentation DLL's entry points (\texttt{DllMain}).
	
	\begin{lstlisting}[language=C++, caption={DllMain code for attaching/detaching instrumentation}, label={lst:dllMain}, basicstyle=\ttfamily\footnotesize, breaklines=true]
		BOOL APIENTRY DllMain (HMODULE hModule,
		DWORD   ul_reason_for_call,
		LPVOID  lpReserved)
		{
			switch (ul_reason_for_call)
			{
				case DLL_PROCESS_ATTACH:
				// Instrumentation framework-specific logic for injecting instrumentation
				break;
				case DLL_PROCESS_DETACH:
				// Instrumentation framework-specific logic for disabling instrumentation
				break;
			}
			
			return TRUE;
		}
	\end{lstlisting}
\end{enumerate}

To force a remote, unaware process to load our instrumentation \ac{DLL}, a technique known as \emph{\ac{DLL} Injection} is utilized.
The most common and reliable method relies both on Dynamic Linking and Windows \ac{API}s functions \texttt{CreateRemoteThread} and \texttt{LoadLibrary}.
The injector process allocates memory in the target, writes the path of the \ac{DLL} into that memory, and spawns a thread (using \texttt{CreateRemoteThread}) pointing to \texttt{LoadLibrary}, which reads and processes the specified DLL path.

\section{Paradigms of Binary Instrumentation}

Modern instrumentation engines generally fall into two broad architectural paradigms:
\begin{itemize}
	\item \emph{Inline API Hooking:} this paradigm involves modifying the original execution flow via localized jumps.
	It patches specific functions in memory, redirecting execution to a custom payload before returning to the original flow.
	\item \emph{Dynamic Binary Instrumentation:} rather than modifying the original binary in place, \ac{DBI} engines copy, recompile, and execute instructions inside a localized sandbox known as a Code Cache.
\end{itemize}

\subsection{Execution Context and CPU State Preservation}

Building upon the constraints of the ABI \cref{sec:abi}, it is necessary to formally define what constitutes the execution context of a running process and why preserving it is paramount to process stability during any paradigm of binary instrumentation.

At any given nanosecond, the exact state of an executing thread is represented by the data held within the CPU's internal registers.
On a x64 architecture, this includes General Purpose Registers, the Instruction Pointer, and various status flags (e.g., \texttt{EFLAGS}).
Collectively, these values are referred to as the \emph{CPU state}.

When an instrumentation framework successfully intercepts the execution flow, it redirects the instruction pointer to the user's custom analysis payload.
Because this payload is a compiled piece of software itself, it inevitably utilizes the CPU registers to perform its own calculations, memory allocations, or logging.
This introduces a critical point of failure known as \emph{register corruption}.
If the custom payload overwrites the contents of a register that the original, interrupted application was actively using (for example, to store an intermediate loop counter or a critical memory pointer), that original data is permanently lost.

When the payload finishes its execution and attempts to restore the original execution flow, the application will blindly continue operating using the corrupted register values.
Therefore, to guarantee process stability, the original CPU state must be flawlessly preserved by the instrumentation framework.

\section{Inline API Hooking Architectures}

Hooking is the specific mechanism used to instrument a function.
A hook allows the redirection of the execution flow from the original code to newly injected analysis code.
A standard inline hook consists of three primary logical components:
\begin{enumerate}
	\item \emph{The Target:} the original function whose execution we wish to intercept.
	The goal is to patch the first 5 to 7 bytes of the target function with an unconditional jump (\texttt{JMP}) to a user-defined payload.
	These initial bytes are restored to the target function once the instrumentation is complete and the framework detaches from the host process.
	\item \emph{The Detour (or Payload):} the custom function injected by the instrumentation framework.
	This function receives the execution flow, inspects the target function's arguments or return value, performs the desired analysis or policy enforcement, and then dictates whether the execution should continue or be blocked.
	\item \emph{The Trampoline:} in the paradigm of inline API hooking, placing an interception branch (\texttt{JMP}) inherently corrupts the target function's prologue.
	To maintain execution continuity, all inline instrumentation frameworks must implement an Out-of-Line Execution Bridge, universally referred to as a \emph{``Trampoline''}.
	Conceptually, the trampoline is a dynamically allocated, executable memory buffer that must fulfills two architectural mandates: it securely relocates the displaced prologue instructions and unconditionally routes the instruction pointer back to the unpatched remainder of the target function.
\end{enumerate}

The manner in which these frameworks handle the CPU state, the \ac{ABI} constraints and the Trampoline defines their underlying architecture.
\subsection{Bare-Metal Hooking: Microsoft Detours and MinHook}
Frameworks like Microsoft Detours and MinHook are specifically designed for Windows x86/x64 and utilize a \emph{``bare-metal'' routing} approach.
In this model, the hooking library has zero awareness of the CPU state or context at runtime.
Consequently, they strictly enforce the \ac{ABI}. The developer must possess precise knowledge of the C/C++ signatures (argument types and return types) and calling conventions (if we need to hook in x86 architecture) of the function being hooked.
Using these two frameworks requires a strict type definition of the target function pointer to avoid stack/register corruption, as illustrated in \cref{lst:detours}.

\begin{lstlisting}[language=C++, caption={Detours/MinHook requires strict ABI compliance.}, label={lst:detours}, basicstyle=\ttfamily\footnotesize, breaklines=true]
	// Strict function pointer definition required by Detours
	static int (WINAPI * TrueMessageBoxW)(HWND, LPCWSTR, LPCWSTR, UINT) = MessageBoxW;
	
	// Strict function pointer definition required by MinHook
	typedef int (WINAPI * MESSAGEBOXW)(HWND, LPCWSTR, LPCWSTR, UINT);
	MESSAGEBOXW fpMessageBoxW = NULL;
\end{lstlisting}

Furthermore, to access the arguments correctly, the hooked version of the function must strictly adhere to the original signature, which is defined in \cref{lst:detours2}.

\begin{lstlisting}[language=C++, caption={Strict ABI compliance even in the Hooked Function}, label={lst:detours2}, basicstyle=\ttfamily\footnotesize, breaklines=true]
	// Detours (same for MinHook)
	int WINAPI HookedMessageBoxW(HWND hWnd, LPCWSTR lpText, LPCWSTR lpCaption, UINT uType)
\end{lstlisting}

The code structure for the hooked function is identical in both frameworks.

In \cref{lst:detours3}, the goal is to intercept a target process's call to \texttt{MessageBoxW} and modify the displayed dialog with custom text (\texttt{customCaption}) and altered options (\texttt{modifiedType}) during the PRE-LOGIC phase.

After this, the trampoline is called, the original function is executed with the modified arguments, and control is returned to the hooked version (POST-LOGIC).

Here, we intercept the user's choice (\texttt{result}), forcing a ``yes'' outcome even if the user pressed ``no'', and return the final result to the target process:

\begin{lstlisting}[language=C++, caption={Detours/MinHook Hooked function structure}, label={lst:detours3}, basicstyle=\ttfamily\footnotesize, breaklines=true]
	// Detours (same for MinHook)
	int WINAPI HookedMessageBoxW(HWND hWnd, LPCWSTR lpText, LPCWSTR lpCaption, UINT uType)
	{
		// PRE-LOGIC
		UINT modifiedType = MB_YESNO;
		LPCWSTR customCaption = L"Hooked! Please choose:";
		
		// Call to the trampoline
		int result = TrueMessageBoxW(hWnd, lpText, customCaption, modifiedType);
		// POST-LOGIC
		if (result == IDNO) 
		{
			std::cout << "[HOOK POST-LOGIC] Intercepted IDNO (No). Changing result to IDYES (Yes)!"
			<< std::endl;
			result = IDYES; 
		}
		else if (result == IDYES)
		{
			std::cout << "[HOOK POST-LOGIC] Intercepted IDYES (Yes). Nothing to do."
			<< std::endl;
		}
		
		return result;
	}
\end{lstlisting}

\subsection{Context-Aware Routing: Frida-Gum}
Frida-Gum is the underlying C library of the Frida instrumentation toolkit, representing a modern approach to cross-platform instrumentation (X86/X64, ARM/ARM64, MIPS).

In contrast to bare-metal routing, Frida-Gum utilizes \emph{``Context-Aware Routing.''} When a hook is triggered, the framework jumps not directly to the custom payload, but into a dynamically allocated memory block containing instructions that save all CPU registers into a hardware-agnostic structure (\texttt{GumInvocationContext}) before invoking the payload.

After the hooking callbacks execute, these saved values are used to restore the CPU state exactly as it was prior to the hook, preventing process crashes.
This context awareness normalizes the \ac{ABI} and abstracts the target process architecture.
The developer could not define strict C++ function signatures;
arguments and return values are accessed and modified dynamically by their index, regardless of the target process architecture.

Due to these architectural differences, the implementation significantly diverges from that of Detours and MinHook.
The developer only needs to specify the \texttt{on\_enter} and \texttt{on\_leave} hooking callbacks: \texttt{on\_enter} executes before the target function, while \texttt{on\_leave} executes after it finishes.
The Frida-Gum equivalent code for altering the behavior of \texttt{MessageBoxW} is implemented in \cref{lst:frida}.

\begin{lstlisting}[language=C, caption={Frida-Gum \texttt{on\_enter}/\texttt{on\_leave} for hooking MessageBoxW.}, label={lst:frida}, basicstyle=\ttfamily\footnotesize, breaklines=true]
	// Pre-logic
	static void
	example_listener_on_enter (GumInvocationContext * ic,
	gpointer user_data)
	{
		// The arguments for MessageBoxW are 0-indexed:
		// 0: HWND hWnd
		// 1: LPCWSTR lpText
		// 2: LPCWSTR lpCaption
		// 3: UINT uType
		
		// Frida-Gum allows contextual argument extraction without strict C signatures
		guint originalType = GPOINTER_TO_UINT (gum_invocation_context_get_nth_argument (ic, 3));
		guint modifiedType = MB_YESNO;
		
		static const wchar_t* customCaption = L"Hooked, choose:";
		
		gum_invocation_context_replace_nth_argument (ic, 2, (gpointer) customCaption);
		gum_invocation_context_replace_nth_argument (ic, 3, GUINT_TO_POINTER (modifiedType));
	}
	
	// Post-logic
	static void
	example_listener_on_leave (GumInvocationContext * ic,
	gpointer user_data)
	{
		int result = GPOINTER_TO_INT (gum_invocation_context_get_return_value (ic));
		if (result == IDNO) 
		{
			g_print ("Intercepted IDNO (No). Changing result to IDYES (Yes)\n");
			gum_invocation_context_replace_return_value (ic, GINT_TO_POINTER (IDYES));
		}
		else if (result == IDYES)
		{
			g_print ("Intercepted IDYES (Yes). Nothing to do\n");
		}
	}
\end{lstlisting}

\subsection{Instruction Boundaries and the Role of Disassemblers}

\note{Advisor}{cyan}{Non so se mettere questa sezione}
A fundamental challenge in implementing the hook structure described above, particularly on Intel x86 and x64 architectures, is the variable-length nature of the instruction set.
To detour a target function, an inline hooking framework typically needs to overwrite the first few bytes of the function's prologue with an unconditional jump (\texttt{JMP}) to the custom payload.
In a standard 32-bit architecture, this jump requires 5 bytes (1 byte for the opcode, 4 bytes for the relative address).
If the framework blindly overwrites exactly 5 bytes, it risks cutting an existing instruction in half.
If the original prologue consists of two 3-byte instructions, overwriting 5 bytes will corrupt the second instruction, leaving a hanging, invalid byte.
When the trampoline attempts to execute these copied bytes to resume the program, the CPU will encounter an invalid opcode and crash the process.
To prevent this, hooking frameworks must incorporate a Length Disassembler Engine (LDE).
Before applying any patches, the engine disassembles the target function's prologue to calculate exact instruction boundaries.
It then copies whole, unfragmented instructions into the trampoline until it has safely relocated at least the number of bytes required for the jump (padding any remaining bytes in the original function with \texttt{NOP} instructions).
The choice of disassembler heavily impacts the footprint and dependencies of the framework:
\begin{itemize}
	\item \emph{Microsoft Detours} relies on a proprietary, internal instruction decoder optimized specifically for standard compiler prologues.
	\item \emph{MinHook} utilizes a highly optimized, custom-built Hacker Disassembler Engine \allowbreak (HDE32/\allowbreak HDE64) to calculate instruction lengths, rather than fully analyze instruction semantics.
	\item \emph{Frida-Gum} requires deep semantic analysis of the instructions to achieve its context-aware routing.
	To accomplish this, it statically links against Capstone, a comprehensive and heavy multi-architecture disassembly framework, significantly increasing the size of the resulting \ac{DLL}.
\end{itemize}

\subsection{Transactional Patching}

Another critical challenge in inline hooking is applying the memory patch (e.g., the \texttt{JMP} instruction) to a live, running process without causing a \emph{race condition}.

In a multi-threaded application, if one thread attempts to execute a target function at the exact moment the instrumentation framework is overwriting its prologue, the CPU may attempt to execute a partially written, invalid instruction.
To guarantee thread safety during the patching phase (both attaching and detaching), modern instrumentation frameworks implement a \emph{transactional model}.

Instead of patching memory directly and immediately, the developer queues the hooks.
When the transaction is finalized, the framework briefly suspends all threads in the target process (except the one applying the patch) and writes the bytes to memory atomically.
Crucially, simply suspending the threads is not sufficient. A thread might have been suspended at the exact moment its Instruction Pointer (\ac{IP}, i.e., \texttt{EIP}/\texttt{RIP}) was pointing to the instructions inside the prologue that are about to be overwritten.
To prevent this, the framework inspects the register context of each suspended thread.
If a thread's \ac{IP} is detected within the address range of the code being replaced, the framework dynamically relocates the \ac{IP} to the corresponding instruction inside the trampoline (when attaching a hook) or back to the restored original instructions (when detaching a hook) before resuming execution.

\emph{Detours} makes this transaction explicitly visible to the developer. The \ac{API} requires opening a transaction, manually declaring which threads need to be stopped, attaching/detaching the specified hooks, and committing the transaction, as illustrated in \cref{lst:detours_lifecycle}.

\begin{lstlisting}[language=C++, caption={Microsoft Detours transactional model for safe attachment and detachment.}, label={lst:detours_lifecycle}, basicstyle=\ttfamily\footnotesize, breaklines=true]
	// --- SAFE ATTACHMENT ---
	// Start the transaction
	DetourTransactionBegin();
	
	// Enlist threads to be suspended during the patch
	DetourUpdateThread(GetCurrentThread()); 
	// here we specify possible other threads we want to stop...
	
	// Queue the hooks
	DetourAttach(&(PVOID&)TrueMessageBoxW, HookedMessageBoxW);
	// here we specify possible other hooks we want to inject...
	
	// Apply patches atomically, suspending the specified threads and flushing the instruction cache
	DetourTransactionCommit();
	
	// --- SAFE DETACHMENT ---
	DetourTransactionBegin();
	
	DetourUpdateThread(GetCurrentThread());
	// here we specify possible other threads we want to stop...
	
	DetourDetach(&(PVOID&)TrueMessageBoxW, HookedMessageBoxW);
	// Queue removal
	// here we specify possible other hooks we want to detach...
	
	DetourTransactionCommit();
	// Suspends threads, restores original bytes, resumes
\end{lstlisting}

\emph{MinHook} abstracts the explicit transaction start and end calls, but enforces the exact same synchronization internally when hooks are enabled or disabled. This behavior is shown in \cref{lst:minhook_lifecycle}.

\begin{lstlisting}[language=C++, caption={MinHook internal thread synchronization during enable/disable phases.}, label={lst:minhook_lifecycle}, basicstyle=\ttfamily\footnotesize, breaklines=true]
	// --- SAFE ATTACHMENT ---
	MH_CreateHook(&MessageBoxW, &HookedMessageBoxW, reinterpret_cast<LPVOID*>(&fpMessageBoxW));
	// here we specify possible other hooks we want to inject...
	
	// MH_EnableHook internally suspends threads, writes the JMP, and resumes
	MH_EnableHook(&MessageBoxW);
	//or MH_EnableHook(MH_ALL_HOOKS); if we have more than one hook
	
	// --- SAFE DETACHMENT ---
	// MH_DisableHook internally suspends threads, restores original bytes, and resumes
	MH_DisableHook(&MessageBoxW);
	//or MH_DisableHook(MH_ALL_HOOKS); if we have more than one hook
\end{lstlisting}

\emph{Frida-Gum} employs an identical safety mechanism through its Interceptor \ac{API}, which is presented in \cref{lst:frida_lifecycle}.

\begin{lstlisting}[language=C, caption={Frida-Gum utilizing transaction boundaries for hook management.}, label={lst:frida_lifecycle}, basicstyle=\ttfamily\footnotesize, breaklines=true]
	// --- SAFE ATTACHMENT ---
	gum_interceptor_begin_transaction (interceptor);
	gum_interceptor_attach (interceptor,
	GSIZE_TO_POINTER (gum_module_find_export_by_name (user32, "MessageBoxW")),
	listener,
	NULL,
	GUM_ATTACH_FLAGS_NONE);
	// here we specify possible other hooks we want to inject...
	
	gum_interceptor_end_transaction (interceptor);
	// Threads are paused and patches applied
	
	// --- SAFE DETACHMENT ---
	gum_interceptor_begin_transaction (interceptor);
	
	gum_interceptor_detach (interceptor, listener);
	// here we specify possible other hooks we want to detach...
	
	gum_interceptor_end_transaction (interceptor);
	// Threads are paused and bytes restored
\end{lstlisting}

\section{Dynamic Binary Instrumentation (DBI) Architectures}

For deeper execution analysis at the assembly level, \ac{DBI} engines are utilized.
Unlike inline hooking, which patches the original binary in place, \ac{DBI} engines ensure that the target application's original code is never executed directly by the CPU.
Instead, the framework employs a \emph{Just-In-Time (JIT) compilation} mechanism to dynamically translate and instrument instruction sequences.
\subsection{Core Architectural Components}
Modern \ac{DBI} frameworks rely on a unified architectural pattern comprising the following components:

\begin{description}
	\item[1. The Dispatcher (Control Flow Manager):] The dispatcher is the central component of the \ac{DBI} engine, responsible for orchestrating the execution state.
	Because the application and the \ac{DBI} framework share the same process but operate under different scopes, they must safely transit between ``framework mode'' and ``application mode''.
	The dispatcher triggers a context-switch mechanism that carefully saves and restores the application's state whenever execution exits or enters the code cache.
	\item[2. \ac{JIT} Compiler:] Instead of translating the entire binary before execution, these architectures translate the application's instructions dynamically in small fragments.
	During this translation phase, the framework decodes and encodes (into the framework's abstraction) the original instructions and has the opportunity to insert custom instrumentation code or patches before emitting the new sequence.
	\item[3. The Code Cache (The Execution Sandbox):] To mitigate the massive performance penalty of repeatedly translating the same code, \ac{DBI} frameworks employ a software-based code cache.
	The translated and potentially instrumented fragments are stored in this sandboxed memory region.
	When the application re-executes a previously translated section of code, it runs directly from the code cache, which significantly optimizes execution speed.
	\item[4. The Client Interface (Instrumentation API):] This is the abstraction layer exposed to the developer.
	It provides the necessary functions to inspect the program state, traverse instruction sequences, and specify exactly where and how instrumentation should be injected.
\end{description}

\subsection{The Execution Lifecycle: The JIT Loop}
To formally describe how these components interact at runtime, we can outline the execution lifecycle of a standard block of code, illustrated in \cref{fig:dbi_flow}:

\begin{enumerate}
	\item \emph{Interception:} The target application attempts to execute a block of original code.
	The \ac{DBI} engine intercepts this attempt and yields control to the Dispatcher.
	\item \emph{Cache Lookup:} The Dispatcher queries a fast-lookup hash table to check if the target memory address has already been translated.
	If it results in a cache hit, the CPU is redirected to the Code Cache.
	\item \emph{Translation (On Cache Miss):} If the code has not been encountered before, the \ac{JIT} Compiler decodes original binary instructions one by one to form a straight-line sequence that terminates at a control transfer, such as a branch, call, or return.
	\item \emph{Instrumentation:} The engine queries the Client Interface to determine if the user wishes to instrument the block or a single instruction within it.
	If so, the instrumentation instructions are injected. 
	\item \emph{Emission and Linking:} Most \ac{DBI} frameworks use this phase to apply patches to the control-flow instructions at the end of the sequence, guaranteeing that when the block finishes running, it will redirect back to the framework rather than jumping to a native memory address.
	If the block ends in a direct branch to another previously translated block, the engine ``links'' them together directly in the cache (if it was an indirect branch, it cannot know the target before executing it), allowing the CPU to bypass the Dispatcher in future iterations.
	The modified block is emitted into the Code Cache.
	\item \emph{Execution:} The Dispatcher performs a context switch, restoring the application state, and commands the CPU to execute the newly cached block natively.
	\item \emph{Code Cache Exit:} Execution remains safely inside the code cache --- often jumping directly from one translated block to another through ``linking''---until it hits a boundary.
	This boundary might be an unlinked branch or an indirect branch whose target hasn't been translated yet.
	When this happens, the block executes an exit stub which saves the CPU's state and transfers control back to the Dispatcher, restarting the loop.
\end{enumerate}

	\centering
	\includegraphics[width=0.9\textwidth]{images/DBI_flow.png}
	\caption{The Execution Lifecycle of a DBI framework}
	\label{fig:dbi_flow}
\end{figure}

While \ac{DBI} frameworks allow a more granular analysis of the target code, they introduce \emph{significantly higher overhead} compared to inline hooking.
Every single instruction of the program needs to be \ac{JIT}-compiled before execution, even if no instrumentation is injected.
\subsection{The Client Interface: Instrumentation vs. Analysis Functions}

\ac{DBI} frameworks require the developer to interact with the engine using a \emph{two-tiered callback paradigm}.
The developer must supply two distinct types of functions to the engine, each operating at fundamentally different times during the execution lifecycle:

\begin{itemize}
	\item \emph{The Instrumentation Function (The ``Where'' and ``What''):} 
	This callback is invoked by the \ac{DBI} engine \emph{only once} per newly discovered sequence of instructions during the \ac{JIT} compilation phase.
	Its purpose is to inspect the static properties of the instructions (e.g., opcodes, operands) and decide \emph{if} and \emph{where} custom code should be injected.
	If injection is required, it uses the \ac{API} to queue the insertion of the analysis function.
	\item \emph{The Analysis Function (The ``Action''):} 
	This is the actual custom payload injected into the Code Cache.
	Unlike the instrumentation function (executed only at compile time), it is executed \emph{every time} the CPU runs the corresponding instrumented block of code.
	For this reason, the analysis function must be heavily optimized and efficient.
\end{itemize}

The level of abstraction provided by the Client Interface significantly alters how developers interact with the engine.
\subsection{High-Level Abstraction API: Intel PIN}
Intel PIN is a standard academic \ac{DBI} framework with a proprietary (free for non-commercial use) license.
It provides a heavily abstracted C++ \ac{API}.

To utilize Intel PIN, developers do not modify the core engine itself.
Instead, they write a custom C++ program known as a \emph{PINtool}.
A PINtool represents the physical implementation of the Client Interface discussed previously;
it is the user-defined module that contains both the Instrumentation Functions and the Analysis Functions.
Architecturally, a PINtool is compiled as a standard shared library (a \ac{DLL} on Windows).
When the user launches a target application under PIN, the engine automatically injects the PINtool \ac{DLL} into the target process's memory space.
Once loaded, the engine invokes the PINtool's \texttt{main} function, allowing the tool to register its specific callbacks.
In \cref{lst:pin_branch}, we can observe the granularity achievable using \ac{DBI}: in this case, we can log conditional branches to determine which paths are taken during code execution.


\begin{lstlisting}[language=C++, caption={An example of a PINtool for branch logging}, label={lst:pin_branch}, basicstyle=\ttfamily\footnotesize, breaklines=true]
	// Analysis function (Runs at execution time in the Code Cache)
	void record_branch(ADDRINT instruction_address, ADDRINT target_address, BOOL taken) {
		
		if (taken) { /* Log Taken */ } 
		else       { /* Log Not Taken */ }
	}
	
	// Instrumentation function (Runs at JIT compilation time)
	void trace(INS instruction, void *v) {
		
		// PIN abstracts away module resolution: we want to instrument
		// only target application instructions, filter possible external libraries
		RTN rtn = INS_Rtn(instruction);
		if (RTN_Valid(rtn) && IMG_IsMainExecutable(SEC_Img(RTN_Sec(rtn)))) {
			// If it is inside the target executable, check if it's an IF branch
			if (INS_IsBranch(instruction) && INS_HasFallThrough(instruction)) {
				// Inject analysis function right before the jump happens.
				INS_InsertCall(instruction, IPOINT_BEFORE, (AFUNPTR)record_branch,
				IARG_INST_PTR,           
				IARG_BRANCH_TARGET_ADDR,  
				IARG_BRANCH_TAKEN,        
				IARG_END);
			}
		}
	}
\end{lstlisting}

\subsection{Bare-Metal API: DynamoRIO}
DynamoRIO is the open-source alternative that exposes a lower-level C \ac{API}.
The equivalent branch-logging example seen previously for PIN is implemented in \cref{lst:dr_branch}.

\begin{lstlisting}[language=C, caption={DynamoRIO branch instrumentation example}, label={lst:dr_branch}, basicstyle=\ttfamily\footnotesize, breaklines=true]
	// Analysis function
	static void record_branch(app_pc instr_addr, app_pc target_addr, int taken) {
		
		if (taken) { /* Log Taken */ } 
		else       { /* Log Not Taken */ }
	}
	
	// Instrumentation function
	static dr_emit_flags_t event_bb_analysis(void *drcontext, void *tag, instrlist_t *bb, instr_t *inst, bool for_trace, bool translating,
	void *user_data) {
		
		// Manual module tracking to filter out OS libraries
		app_pc instr_addr = instr_get_app_pc(inst);
		module_data_t *mod = dr_lookup_module(instr_addr);
		bool is_main_exec = false;
		
		if (mod != NULL) {
			module_data_t *main_mod = dr_get_main_module();
			if (main_mod != NULL) {
				if (mod->start == main_mod->start) { is_main_exec = true;
				}
				dr_free_module_data(main_mod);
			}
			dr_free_module_data(mod);
		}
		
		if (!is_main_exec) return DR_EMIT_DEFAULT;
		// Check if it's a conditional branch (CBR)
		if (instr_is_cbr(inst)) {
			// Inject analysis function into the basic block (bb)
			dr_insert_cbr_instrumentation(drcontext, bb, inst, (void *)record_branch);
		}
		return DR_EMIT_DEFAULT;
	}
\end{lstlisting}

Using DynamoRIO, developers can directly manipulate the instruction flow.
In PIN, developers generally ``wra'' existing instructions (adding a call before or after an instruction) but cannot easily modify the instruction itself. 
In DynamoRIO, the developer is handed a linked list of instructions (\texttt{instrlist\_t}) and can easily manipulate or modify them (e.g., reordering them or moving a load instruction earlier to test for race condition).

Furthermore, because PIN is designed to be highly opaque, using \texttt{INS\_InsertCall} prompts PIN's \ac{JIT} compiler to automatically analyze the custom analysis function for deciding which registers need to be saved and restored based on what the C++ code actually uses. 
With DynamoRIO, developers can manage the 
state and flags manually for specialized analysis.

In conclusion, while DynamoRIO may present a steeper learning curve than Intel PIN, it affords developers greater transparency and raw power, providing fine-grained control over the translated code and the code cache.

\section{Experimental Validation}
\label{sec:experimental_validation}

To empirically validate the theoretical concepts discussed in the preceding sections and to fully understand the operational constraints, security boundaries, and low-level deployment challenges of each framework, a propedeutic suite of testing applications was developed. All source code and custom injection utilities have been organized and made available within the project's repository.\footnote{\url{https://github.com/davde342/MasterThesis/tree/main/code/first_examples}} 

The experimental activity was structured into three different scenarios, each designed to isolate and evaluate specific architectural properties of the instrumentation engines.

\subsection{Scenario 1: Single-Threaded Hooking and Process Injection/Ejection Mechanics}
\label{subsec:scenario_1}

\begin{itemize}
	\item \textbf{Test Rationale:} This preliminary scenario aimed to verify the fundamental lifecycle management of binary instrumentation within the Windows ecosystem. 
	
	This involved implementing a custom, dual-mode utility (\texttt{injector.cpp}) to handle both the insertion and the ejection of the instrumentation payload. 
	
	Concurrently, the test evaluated the syntactic and structural paradigms of the three inline hooking frameworks (Microsoft Detours, MinHook, and Frida-Gum) when intercepting a standard system API—\texttt{MessageBoxW} in \texttt{user32.dll}.
	
	\item \textbf{Empirical Results:} Every analyzed framework successfully intercepted the execution flow during the ``Pre-Logic'' phase. This capability allowed for the modification of string pointers targeting the dialog box text and caption, the reassignment of the configuration flags to \texttt{MB\_YESNO}, and the runtime mutation of the return value during the ``Post-Logic'' phase, effectively forcing an \texttt{IDYES} outcome regardless of the user's explicit interaction. 
	
	Furthermore, forcing the programmatic module ejection successfully triggered the \texttt{DLL\_PROCESS\_DETACH} branch within each hook's entry point, safely restoring the original prologue instruction bytes and confirming a flawless ejection in single-threaded environments.
	
	\item \textbf{Encountered Obstacles:} In this idealized single-threaded scenario, no big challenges occurred. Setting up Microsoft Detours was straightforward due to its thoroughly documented APIs, the abundance of reference examples, and a bare-metal paradigm that is conceptually simpler than that of Frida-Gum. 
	
	MinHook demonstrated a similar workflow to Detours but simplified the implementation further by automatically managing transactional patching internally. 
	
	Conversely, approaching Frida-Gum for the first time presented a steeper learning curve; given its more complex architecture, distinct paradigm, and less exhaustive documentation; comprehensively understanding its API behaviors and mapping them to my use case required a direct analysis of the huge and dense codebase within the official Frida repository.
\end{itemize}

\subsection{Scenario 2: Multi-Threaded Hooking and Concurrency Management}
\label{subsec:scenario_2}

\begin{itemize}
	\item \textbf{Test Rationale:} To simulate a realistic production workload and test the instrumentation frameworks under thread concurrency, a multithreaded target engine was used (\texttt{target\_multithread.cpp}). This target utilizes a synchronized task queue where a producer thread continuously queues activities with varying workloads, while three concurrent consumer threads process these tasks in parallel by invoking the exported routines \texttt{ProcessTask} and \texttt{LogTaskResult}.
	
	\item \textbf{Empirical Results:} Real-time monitoring of thread behaviors was achieved, allowing a dynamic optimization policy: the injected hook intercepted high-latency tasks (>500ms) and programmatically constrained their complexity metrics to 100ms prior to native routing, illustrating the possibility of inline hooking for runtime policy enforcement and load adaptation.
	
	\item \textbf{Encountered Obstacles:} Two major obstacles I faced in this scenario. First, performing hook detachment (\texttt{DetourDetach} in Microsoft Detours) in a concurrent context introduced a possible race condition: active worker threads could be descheduled while executing inside the hook callback, causing an immediate Access Violation (\texttt{0xC0000005}) once the library was unmapped. 
	
	Second, in Frida-Gum, intercepting routines that process floating-point arguments (such as the \texttt{double} parameter in \texttt{LogTaskResult}) encountered an ABI mismatch because these parameters are passed via \texttt{XMM0}--\texttt{XMM3} registers under the Windows x64 ABI, while Frida expects them in other registries.
	
	\item \textbf{Implemented Mitigations:} To address the detachment race condition, an RAII-based safety synchronization primitive (\texttt{HookGuard}) was implemented using an atomic execution counter (\texttt{g\_ActiveHooks}), for keeping track of threads inside the Hook logic; during \texttt{DLL\_PROCESS\_DETACH}, the payload enters a spin-wait loop and a grace period (\texttt{Sleep}/\texttt{SwitchToThread}) to ensure all threads exit the hook scope before module unloading. 
	
	To bypass the floating-point register limitation in Frida-Gum, the high-level callback attachment was discarded in favor of full function replacement (code become similar to Detours/MinHook) via \texttt{gum\_\allowbreak interceptor\_\allowbreak replace}, to let the compiler handle the exact register alignment natively.
\end{itemize}

\subsection{Scenario 3: Instruction-Level Assembly Tracking via DBI Engines}
\label{subsec:scenario_3}

\begin{itemize}
	\item \textbf{Test Rationale:} To achieve low-level instruction granularity, a target program containing conditional branches was compiled (\texttt{PIN\_\allowbreak dynamo\_\allowbreak target.cpp}), alongside an Intel PIN tool (\texttt{pintool.cpp}) and a DynamoRIO client (\texttt{dynamo.c}). The rationale was to program the underlying JIT compilers to isolate all conditional branch instructions (\texttt{INS\_IsBranch} / \texttt{instr\_is\_cbr}) and dynamically inject an analysis callback (\texttt{record\_branch}) used to log the target address (taken branch).
	
	\item \textbf{Empirical Results:} Both \ac{DBI} engines yielded execution trace graphs. Using IntelPIN it was also possible to write the source file code line number correspondent to the taken branch
	
	\item \textbf{Encountered Obstacles:} An initial operational challenge involved navigating the different APIs of the two frameworks; DynamoRIO exposes lower-level, bare-metal utilities compared to the highly abstracted API of Intel PIN, resulting in a steeper learning curve. Beyond API familiarity, the primary technical obstacle across both engines was attempting to log not only the target runtime address of each taken branch but also its source code line number from \texttt{PIN\_dynamo\_target.cpp} (compiled with debug symbols) to maximize execution trace readability.
	
	\item \textbf{Implemented Mitigations:} After several unsuccessful attempts, I have found that for solving the source line number obstacle under Intel Pin, I had to utilize the \texttt{PIN\_GetSourceLocation} API. However, direct invocation of this routine inside the analysis function triggers a critical runtime error due to missing client locks. To mitigate this, calls to \texttt{PIN\_GetSourceLocation} were wrapped inside a thread-safe synchronization pair using \texttt{PIN\_LockClient()} and \texttt{PIN\_UnlockClient()}, ensuring proper access to Pin's symbol database.
\end{itemize}
